# LAFAms – User Roles, Permissions & Account Lifecycle

**Version:** 1.0  
**System Roles:** ADMIN, STAFF, CUSTOMER  
**Authorization Model:** Role-Based Access Control (RBAC) + Privilege-Based Authorization

---

## 1. User Roles Overview

LAFAms has three primary user roles:

1. ADMIN – Highest authority and system administrator.
2. STAFF – Operational user responsible for daily financial and customer activities.
3. CUSTOMER – Read-only user who accesses personal financial information.

Every authenticated account must have an assigned role and an appropriate account status.

---

## 2. ADMIN Role

### Purpose

Admin is the highest-authority user responsible for managing the institution's system, staff, customers, business decisions, permissions, and approvals.

### Admin Responsibilities

**System Management**

- Access the complete administrative dashboard.
- Manage system-level settings.
- Manage approved business rules.
- Manage operational configurations.
- View system activities and audit records.

**Staff Management**

- Create staff accounts.
- Update staff information.
- Set up and reset staff passwords.
- Activate and deactivate staff accounts.
- Assign roles and privileges.
- Modify staff permissions.
- Revoke staff sessions.

**Customer Management**

- Create and manage customer accounts.
- Set up and reset customer passwords.
- Activate and deactivate customer accounts.
- Approve customer account activation.
- Manage customer information.
- Review KYC information.
- Manage customer account lifecycle.

**Financial Management**

- Manage loans.
- Manage repayments.
- Manage gold collateral.
- Manage current accounts.
- Manage fixed deposits.
- Manage financial operations.
- View financial histories.

**Approval Management**

- Review staff update requests.
- Approve or reject restricted changes.
- Review backdated repayment requests.
- Approve authorized corrections.
- Maintain accountability for decisions.

**Audit Management**

- View audit logs.
- Review staff activities.
- Track sensitive account changes.
- Monitor approvals and rejections.

### Admin Restrictions

- Only one Admin account is permitted.
- Admin does not require customer/staff KYC registration.
- Admin creation must use the controlled bootstrap process.
- The application must prevent unauthorized creation of another Admin.

---

## 3. STAFF Role

### Purpose

Staff performs daily institutional operations and manages customers within assigned privileges.

### Staff Permissions

**Customer Management**

- Register new customers.
- Create customer portal accounts.
- Update permitted customer information.
- View customer records.
- Upload required customer documents and photographs.
- View KYC status.
- Submit restricted customer updates for Admin approval.

**Customer Account Lifecycle**

- Initiate customer account creation.
- Manage customer account activities within assigned privileges.
- Request or perform permitted customer activation and deactivation actions.
- Assist with customer password setup and reset according to assigned privileges and security procedures.
- Customer activation must follow the Admin approval requirement.

**Loan Management**

- Create loan records.
- View loan records.
- Update permitted loan information.
- Submit restricted loan changes for approval.

**Repayment Management**

- Record customer repayments.
- View repayment histories.
- Submit repayment correction requests.
- Submit backdated repayment requests for Admin approval.

**Gold and Collateral**

- Register collateral.
- View collateral information.
- Update permitted collateral details.
- Submit restricted changes for approval.

**Deposit Management**

- Create and manage permitted current-account records.
- Create and manage permitted fixed-deposit records.
- Record authorized operational transactions.
- View deposit histories.

**Operations**

- Record authorized financial activities.
- Manage remittance records.
- Manage permitted inventory records.
- View operational information.

### Staff Restrictions

Staff cannot:

- Create another Admin account.
- Change Admin-controlled business rules.
- Assign themselves higher privileges.
- Modify permissions beyond their authority.
- Bypass Admin approval.
- Approve their own restricted requests.
- Delete financial history.
- Access another staff member's restricted information without permission.
- Access customer information outside authorized operational privileges.

---

## 4. CUSTOMER Role

### Purpose

Customers use the customer portal to view their own account and financial information.

### Customer Permissions

Customers can:

- Log in and log out.
- View their own profile.
- View their own KYC verification status.
- View their own loan records.
- View their own gold collateral information.
- View their own current-account information.
- View their own fixed-deposit information.
- View their own transaction history.
- View their own repayment history.
- View relevant notifications.

### Customer Restrictions

Customers cannot:

- Register themselves publicly.
- Create other users.
- Modify financial records.
- Create loans.
- Record repayments.
- Modify collateral records.
- Modify deposit records.
- Approve requests.
- Access other customers' information.
- Access staff or administrative dashboards.

Customer access must be verified through the authenticated session and database ownership relationships.

A customer must never gain access to another customer's records by changing a URL parameter or request identifier.

## 6. Account Lifecycle

### 6.1 Admin Account Lifecycle

1. System administrator runs the controlled bootstrap command.
2. Admin account is created.
3. The system checks that an Admin does not already exist.
4. Admin establishes secure credentials.
5. Admin logs in.
6. Admin manages staff and customer accounts.
7. Admin can update credentials and account status through authorized processes.

Only one Admin account is permitted.

### 6.2 Staff Account Lifecycle

1. Admin creates a staff account.
2. Staff profile information is registered.
3. Required staff documents and photographs are collected.
4. Admin establishes or authorizes initial password setup.
5. Staff account is activated by Admin.
6. Staff logs in.
7. Staff receives assigned privileges.
8. Staff performs authorized operational activities.
9. Admin can update staff information, permissions, credentials, or account status.
10. Deactivated staff cannot access protected system functions.

### 6.3 Customer Account Lifecycle

1. Staff registers a customer.
2. Customer profile is created.
3. Required customer information and KYC documents are collected.
4. Staff creates a linked customer portal account.
5. Customer account enters a pending approval state.
6. Admin reviews the registration and required information.
7. Admin approves or rejects the activation request.
8. After approval, the account becomes active.
9. Customer receives authorized login credentials through a secure process.
10. Customer logs in and accesses their own information.
11. Staff and Admin manage customer accounts within their respective privileges.
12. Admin can deactivate or reactivate the account.
13. Historical customer and financial records remain preserved.

**Important:** A customer profile and customer login account are separate concepts. A customer may exist in the institutional database without having an active portal account.

## 7. Account Statuses

Recommended account statuses:

| Status    | Meaning                                              |
| --------- | ---------------------------------------------------- |
| PENDING   | Created but awaiting approval                        |
| ACTIVE    | Authorized to access the system                      |
| INACTIVE  | Temporarily disabled                                 |
| REJECTED  | Approval denied                                      |
| SUSPENDED | Access blocked due to administrative/security action |

The backend must validate status before granting access.

A deactivated account must not continue using an existing session.

---

## 8. Approval Lifecycle

Restricted changes must follow an approval workflow.

### Process

1. Staff initiates a restricted change.
2. System records an update request.
3. Request is assigned PENDING status.
4. Admin reviews the request.
5. Admin approves or rejects it.
6. Approved changes are applied through a controlled backend operation.
7. Rejected requests remain recorded.
8. The system records the decision and responsible user in the audit log.

### Approval Requirements

Admin approval is required for:

- Customer portal activation.
- Restricted customer profile modifications.
- Backdated repayments.
- Restricted repayment corrections.
- Other Admin-controlled business decisions.

Staff must not approve their own restricted requests.

## 9. Privilege-Based Authorization

Role alone is not sufficient for every operation.

The system should support individual permissions, such as:

- customer.create
- customer.view
- customer.update
- customer.activate
- customer.deactivate
- loan.create
- loan.view
- loan.update
- repayment.create
- repayment.correct
- repayment.backdate
- collateral.manage
- deposit.manage
- staff.manage
- permissions.assign
- approvals.review
- audit.view
- settings.manage

Permissions must be checked on the backend.

Frontend route protection is only a user-interface convenience and must never be treated as the security boundary.

---

## 10. Account Security Rules

- Passwords must be hashed.
- Passwords must never be visible in plain text to Admin or Staff.
- Password setup and reset must use secure procedures.
- Sessions must be invalidated after account deactivation.
- Permission changes must take effect immediately or after session revocation.
- Customers must only access their own records.
- Staff must only access permitted operational information.
- Sensitive account changes must be audited.
- Failed login attempts must be controlled.
- Administrative actions must be traceable.

---

## 11. Important Development Rule

The permission system must be designed centrally.

Do not scatter hardcoded role checks throughout the application.

Use reusable authorization middleware and permission services.

Every sensitive API endpoint must verify:

1. Authentication.
2. Account status.
3. User role.
4. Required permission.
5. Resource ownership where applicable.
6. Approval status where required.

The database and backend are the final authority for access control.
