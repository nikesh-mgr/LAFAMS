# LAFAms – Production Requirements & Deployment Plan

**Version:** 1.0  
**Current Status:** Development Build  
**Target:** Secure Production Deployment  
**Application Type:** Financial Management System  
**Technology:** React, Node.js, Express, Prisma, MySQL

---

## 1. Production Readiness Objective

Production deployment means making LAFAms available to real institutional users with reliable security, data integrity, availability, backup, monitoring, and recovery procedures.

A successful development build does not automatically mean the application is production-ready.

Before launch, all critical business workflows, security controls, database operations, and recovery procedures must be tested.

### Production Goals

- Secure customer and staff information.
- Prevent unauthorized financial operations.
- Protect database records.
- Maintain transaction history.
- Ensure reliable application availability.
- Prevent unauthorized account access.
- Provide recoverable encrypted backups.
- Monitor application errors and suspicious activities.
- Maintain documented operational procedures.

## 2. Production Requirements

### 2.1 Application Security

The following controls must be implemented and verified:

- HTTPS for all production traffic.
- Secure password hashing.
- Secure server-side sessions.
- HTTP-only cookies.
- Secure cookie configuration.
- CSRF protection.
- Restricted CORS origins.
- Helmet security headers.
- Authentication rate limiting.
- Input validation using Zod.
- Secure file upload validation.
- Protected customer documents.
- Backend role and permission enforcement.
- Customer resource ownership verification.
- Safe error handling.
- No stack traces or internal details exposed to users.
- No hardcoded credentials or secrets.
- Dependency vulnerability review.

### 2.2 Admin Security

Admin has the highest system authority.

Production security requirements:

- Strong Admin password.
- Controlled Admin bootstrap.
- Only one Admin account.
- Administrative actions recorded in audit logs.
- Secure session management.
- Restricted administrative access.
- Admin two-factor authentication.

**Current status:** Admin 2FA is deferred by project-owner decision. It remains a production security gap that must be explicitly addressed before production approval.

### 2.3 Database Security

Database: MySQL 8.4.

Requirements:

- Separate development, staging, and production databases.
- Production database credentials must be different from development credentials.
- Use a dedicated application database user with minimum required privileges.
- Do not expose MySQL publicly.
- Use strong database credentials.
- Enforce foreign-key relationships.
- Apply appropriate unique constraints and indexes.
- Use transactions for related financial operations.
- Review every production migration.
- Restrict database administrative access.
- Monitor database availability and storage.

### 2.4 Document and Image Security

Customer documents contain sensitive information.

Requirements:

- Validate file type.
- Validate file size.
- Validate uploaded content.
- Generate safe file names.
- Restrict document access to authorized users.
- Protect document storage.
- Encrypt sensitive stored document bytes.
- Maintain SHA-256 integrity verification.
- Avoid exposing private document URLs publicly.
- Store customer profile photographs through Cloudinary with appropriate access controls.

### 2.5 Session and Account Security

- Use server-side sessions stored in MySQL.
- Use HTTP-only cookies.
- Apply Secure and SameSite cookie settings appropriate to deployment.
- Implement session expiration.
- Regenerate sessions after authentication.
- Invalidate sessions on logout.
- Revoke sessions after account deactivation.
- Revoke sessions after sensitive permission changes.
- Prevent inactive users from accessing the application.

### 2.6 Financial Data Integrity

Financial records require special protection.

Requirements:

- Use database transactions for related financial operations.
- Prevent duplicate submissions where necessary.
- Validate transaction amounts.
- Validate customer and account relationships.
- Maintain repayment history.
- Maintain transaction references.
- Audit sensitive modifications.
- Restrict deletion of financial records.
- Prefer closing or marking records inactive.
- Require authorized approval for restricted corrections.
- Verify database consistency after migrations and restores.

### 2.7 Backup and Recovery

The current backup approach includes:

- Database backup command: `npm run db:backup`
- Encrypted backup format: `.lafbak`
- Encryption: AES-256-GCM
- Backup and document encryption keys must be separate.
- Restore requires explicit target database confirmation using `--confirm-replace=<DB_NAME>`.

Production requirements:

- Automated scheduled backups.
- Encrypted backup storage.
- Off-server backup copies.
- Restricted backup access.
- Backup integrity verification.
- Backup retention policy.
- Documented restore procedure.
- Periodic restore rehearsals.
- Recovery verification after restoration.

**Important:** A successful backup command does not prove that recovery works. A database-backed restore rehearsal has not yet passed in the current development environment.

Never test restoration against the live production database.

## 3. Infrastructure Requirements

### 3.1 Production Server

The production environment must provide:

- Supported Linux server or managed hosting environment.
- Adequate CPU and RAM.
- Persistent storage.
- Firewall configuration.
- SSH key-based administration.
- Restricted server access.
- Automatic security updates where appropriate.
- Process supervision.
- Log management.
- Monitoring.

Server specifications should be selected according to expected users, transaction volume, database size, and budget.

### 3.2 Web Server and HTTPS

Use a reverse proxy such as Nginx or an equivalent managed hosting service.

Responsibilities:

- Serve the frontend.
- Forward API requests to Express.
- Enable HTTPS.
- Redirect HTTP to HTTPS.
- Apply request-size limits.
- Configure appropriate security headers.
- Support certificate renewal.

### 3.3 Application Process Management

The Node.js backend must run under a process manager or service supervisor.

Requirements:

- Automatic restart after unexpected failure.
- Controlled application startup.
- Graceful shutdown.
- Centralized logs.
- Production environment configuration.
- Health-check endpoint.

Do not run the development server or Nodemon in production.

### 3.4 Environment Variables

Production secrets must not be committed to Git.

Required configuration includes:

- NODE_ENV=production
- DATABASE_URL
- SESSION_SECRET
- BUSINESS_TIME_ZONE=Asia/Kathmandu
- FRONTEND_URL
- CORS_ALLOWED_ORIGINS
- Cloudinary credentials
- Backup encryption key
- Document encryption key

SESSION_SECRET must contain at least 32 characters.

All required variables must be validated during application startup.

Use secure platform environment settings or a secrets manager.

## 6. Production Data Migration

If existing handwritten registers or previous digital records are migrated:

1. Identify the original records.
2. Define the data structure.
3. Clean and validate information.
4. Identify duplicate customers.
5. Assign unique customer identifiers.
6. Verify financial balances against source records.
7. Import customer information.
8. Import approved financial histories.
9. Verify customer relationships.
10. Reconcile imported records.
11. Obtain authorized confirmation.

Never assume imported financial information is correct without reconciliation.

Keep original records available according to the institution's approved retention policy.

## 8. Production Release Approval

Production launch must not be based only on whether the application runs successfully.

The following approvals are required:

1. Functional testing approval.
2. Database integrity approval.
3. Security review approval.
4. Backup and recovery approval.
5. Infrastructure approval.
6. Business workflow approval.
7. Institutional operational approval.

### Final Release Criteria

- Critical functionality works.
- All three user roles are verified.
- Unauthorized access is prevented.
- Financial operations are tested.
- Audit logging works.
- Production configuration is secure.
- Backups can be restored.
- Recovery responsibilities are defined.
- Outstanding security risks are formally assessed.
- The institution authorizes production use.

**Production status must remain NOT READY until all mandatory release criteria have been satisfied or formally accepted by the responsible institution.**

---

## 9. Production Philosophy

LAFAms is a financial system, not just a CRUD application.

Production quality requires more than working frontend pages and backend APIs.

The system must protect:

- Customer identity.
- Financial information.
- Institutional records.
- Staff accountability.
- Transaction integrity.
- Business decisions.
- Data availability and recoverability.

Security, correctness, and recoverability take priority over rapid deployment.

A controlled, tested release is better than an early deployment that risks real institutional data.
