# LAFAms – Backend Development Phases

## Project Overview

LAFAms is a secure, single-branch financial management system designed to digitize customer records, loan operations, deposit accounts, inventory, and administrative activities.

The backend will use a modular architecture with centralized authentication, authorization, validation, business logic, database operations, and audit logging.

### Core Development Principles

- Security-first backend development.
- MongoDB with Mongoose for database management.
- Node.js and Express.js using ES Modules.
- Use `const` by default and arrow functions assigned to `const`.
- Prefer named exports.
- Maintain reusable services and modular controllers.
- Validate all incoming requests.
- Enforce permissions on the backend, not only the frontend.
- Record important financial and administrative activities.
- Never invent financial policies or business rules.
- Preserve financial transaction history.
- Build an MVP first while maintaining a production-ready architecture.
- Single institution and single branch, with scalable architecture.

# Phase 2: Authentication and Permission Setup

### Objective

Implement secure authentication, session management, and centralized permission control.

### Development Tasks

1. Implement secure password hashing.
2. Implement login and logout.
3. Implement server-side session authentication.
4. Use secure HTTP-only cookies.
5. Implement session expiration.
6. Implement session revocation.
7. Implement CSRF protection.
8. Create authentication middleware.
9. Create role-based authorization middleware.
10. Create permission-based authorization middleware.
11. Establish a centralized permission catalog.
12. Implement account status checks.
13. Implement login attempt protection.
14. Prevent unauthorized access to protected APIs.

### Main Roles

- ADMIN
- STAFF
- CUSTOMER

### Permission Principles

**ADMIN**

- Full administrative authority.
- Manages staff and customer accounts.
- Controls business rules and system settings.
- Approves restricted operations.
- Accesses administrative records and audit logs.

**STAFF**

- Accesses permitted operational modules.
- Registers customers.
- Manages permitted customer records.
- Creates and manages permitted loan and deposit records.
- Records payments and submits restricted update requests.
- Cannot modify Admin-controlled decisions.

**CUSTOMER**

- Read-only access to their own records.
- Views profile and KYC status.
- Views loans, collateral, deposits, and transaction history.
- Cannot modify financial or administrative records.

### Completion Requirements

- Authentication works.
- Sessions are secure.
- Role-based permissions work.
- Permission-based access works.
- Inactive accounts cannot log in.
- Unauthorized requests are rejected.
- Customer access is restricted to their own data.

# Phase 3: Complete User Account Management

### Objective

Build the complete lifecycle of Admin, Staff, and Customer accounts.

### 3.1 Admin Account

- Only one Admin account is allowed.
- Admin is created through a secure bootstrap process.
- Admin does not require KYC.
- Admin manages system-wide settings.
- Admin manages Staff and Customer accounts.
- Admin can activate and deactivate accounts.
- Admin can update account details.
- Admin can manage permissions.
- Admin can revoke active sessions.

### 3.2 Staff Account

- Admin creates Staff accounts.
- Admin manages Staff activation and deactivation.
- Admin assigns and updates Staff permissions.
- Staff accounts contain required personal information.
- Staff profile image and citizenship document are supported.
- Staff can access only authorized modules.
- Staff can register customers.
- Staff cannot modify Admin-controlled business decisions.

### 3.3 Customer Account

- Customers are registered by Staff or Admin.
- No public customer self-registration.
- Customer accounts are linked to a customer profile.
- Customer profile contains personal and KYC information.
- Customer profile image and citizenship document are supported.
- Customer account activation follows the configured approval workflow.
- Staff can submit customer account update requests.
- Admin can approve or reject restricted requests.
- Admin can activate and deactivate customer accounts.

### 3.4 Customer-Centered Data Structure

A single Customer record must be linked to all relevant modules.

Customer relationships include:

- Gold Loans
- Land Loans
- Current Accounts
- Fixed Deposits
- Transactions
- Payments
- KYC Documents

Avoid duplicating customer information in different modules.

### Completion Requirements

- Admin bootstrap works.
- Only one Admin can exist.
- Staff lifecycle works.
- Customer lifecycle works.
- Account activation and deactivation work.
- Permission assignment works.
- Customer relationships are correctly maintained.
- Approval workflows work.
- Historical records are preserved.

# Phase 8: Audit Logs and Admin Notifications

Implement centralized activity tracking, security monitoring, and administrative notifications.

### Development Tasks

1. Create Audit Log model.
2. Record user ID and role.
3. Record action type.
4. Record affected module.
5. Record affected record ID.
6. Record timestamp.
7. Record relevant changes.
8. Record approval and rejection actions.
9. Record account activation and deactivation.
10. Record permission changes.
11. Record financial operations.
12. Record security-related events.
13. Protect audit logs from unauthorized modification.

### Important Principle

Audit logs must be generated on the backend. Do not depend on frontend-generated audit messages.

Never store plaintext passwords, session tokens, or sensitive authentication credentials in logs.

## Development Execution Rule

Complete one phase before moving to the next.

For each phase:

1. Review the requirements.
2. Identify required models and relationships.
3. Implement database models.
4. Implement validators.
5. Implement services and business logic.
6. Implement controllers.
7. Implement routes and middleware.
8. Test permissions and security.
9. Test successful and failed operations.
10. Review and finalize the phase.

**Important:** Do not move financial policies into code without explicit Admin/business-owner decisions. Keep MVP limitations documented and implement additional financial calculations only after their rules are approved.
